Module 1.1 ~25 min · Theory

📡 The Integration Problem

Understand why connecting AI models to external tools became an increasingly difficult and unsustainable problem.

What it is:

AI integrations are bridges that let language models connect to external systems — databases, APIs, productivity tools, and any other software. Without integrations, a model is limited to what it already knows.

Why learn:

Understanding the concept of integrations is the first step toward understanding why MCP exists. You need to know the problem before you can appreciate the solution.

Key concepts:

Language model, external systems, APIs, tools, real-time data, automated actions.

What it is:

Before MCP, each integration between an AI model and an external tool was built individually. Each developer created their own bridge, with its own format, authentication, and communication logic.

Why learn:

Understanding the landscape before MCP reveals the pain that led to its creation. You'll see how repetitive, fragmented work consumed enormous resources.

Key concepts:

Ad hoc integration, boilerplate code, lack of standardization, rework, tight coupling.

What it is:

The N×M problem occurs when each of the N AI models needs a specific integration for each of the M available tools. The total number of required integrations grows multiplicatively, making the ecosystem unsustainable.

Why learn:

This is the central problem MCP solves. Understanding it is essential to appreciating the elegance of the N+M solution the protocol offers.

Key concepts:

Combinatorial complexity, exponential growth, N×M vs. N+M, scalability, maintenance.

What it is:

Fragmented integrations create enormous costs: development time wasted recreating solutions, money spent maintaining duplicated code, and growing complexity that makes it harder to evolve systems.

Why learn:

Quantifying the costs of fragmentation helps justify MCP adoption in any organization. It’s the business case behind the technical decision.

Key concepts:

Maintenance cost, technical debt, time to market, duplicated effort, organizational scalability.

What it is:

Before MCP, several approaches tried to solve the integration problem: generic REST APIs, platform-specific SDKs, proprietary plugins like ChatGPT's, and function-calling frameworks. Each solved part of the problem but created new ones.

Why learn:

Knowing about previous attempts shows why they failed to be universal and how MCP learned from each one to create something better.

Key concepts:

REST APIs, SDKs, plugins, function calling, platform lock-in, interoperability.

What it is:

Just as USB standardized physical connections and HTTP standardized the web, AI integration with external tools needed a universal protocol. The need for an open, extensible, and platform-agnostic standard was inevitable.

Why learn:

Understanding why a standard was inevitable helps you see MCP not as a passing technology, but as a fundamental part of the AI infrastructure of the future.

Key concepts:

Open protocol, standardization, interoperability, network effect, ecosystem, universal adoption.

Module 1.2 ~25 min · Theory

🔌 MCP as a Universal Standard

Learn about the Model Context Protocol, its origins and purpose, and how it transforms the way AI models connect to the world.

What it is:

The Model Context Protocol (MCP) is an open protocol that standardizes how AI models communicate with external tools, data, and services. It defines a universal interface that any model can use to access any compatible tool.

Why learn:

This is the fundamental definition of what you’ll build throughout the course. Understanding what MCP is ensures you grasp each concept that follows.

Key concepts:

Model Context Protocol, open protocol, universal interface, integration standardization, JSON-RPC.

What it is:

Just as USB created a universal connector for physical devices, MCP creates a “universal connector” for AI integrations. Before USB, each manufacturer had its own cable. MCP does the same for the world of language models.

Why learn:

The USB analogy is the most intuitive way to explain MCP to anyone. Mastering it enables you to communicate the protocol’s value to developers and non-developers.

Key concepts:

USB analogy, universal connector, plug-and-play, compatibility, open ecosystem.

What it is:

MCP was created by Anthropic, the company behind Claude. The motivation came from the need to let Claude and other models connect to external tools securely, consistently, and extensibly, without relying on proprietary solutions.

Why learn:

Knowing MCP's origins and motivation helps you understand its design decisions and why it's an open protocol rather than a proprietary product.

Key concepts:

Anthropic, open protocol, open source, security-centered design, extensibility.

What it is:

MCP transforms the N×M problem into N+M. Instead of each model needing a specific integration for each tool, each model implements MCP once and each tool implements MCP once. They all connect automatically.

Why learn:

This is MCP’s core value proposition. Understanding the transformation from N×M to N+M is essential to explain why the protocol matters.

Key concepts:

N+M vs. N×M, reduced complexity, standardized interface, reuse, composability.

What it is:

The MCP ecosystem is growing rapidly. Companies like Anthropic, tools like Cursor and Windsurf, and various open source projects have already adopted the protocol. The number of available MCP Servers grows every week.

Why learn:

Knowing who is adopting MCP validates the technology and shows that it’s not just a theoretical specification—it’s a reality in production.

Key concepts:

MCP ecosystem, enterprise adoption, Cursor, Claude Desktop, MCP Servers, open source community.

What it is:

MCP is on its way to becoming the de facto standard for AI integrations. New capabilities like native authentication, a server marketplace, and integration with autonomous agents are on the protocol’s roadmap.

Why learn:

Understanding the future of MCP makes you an early adopter. Those who master the protocol now will be prepared for the opportunities that come with its widespread adoption.

Key concepts:

MCP roadmap, server marketplace, authentication, autonomous agents, de facto standard, protocol evolution.

Module 1.3 ~30 min · Theory

🏗️ Host → Client → Server Architecture

Dive into the three pillars of MCP architecture and understand how each component connects to create the complete flow.

What it is:

The Host is the application that hosts the AI model — such as Claude Desktop, Cursor, or any IDE that integrates an LLM. It’s the environment where you interact and where tool requests originate.

Why learn:

Understanding the Host's role is essential to knowing where MCP fits in the stack. Every MCP flow starts and ends at the Host.

Key concepts:

Host application, runtime environment, Claude Desktop, Cursor, user interface, lifecycle.

What it is:

The Client is the component inside the Host that manages communication with MCP Servers. It sends requests, receives responses, and translates between the model’s format and the MCP protocol. Each connection to a Server has its own Client.

Why learn:

The Client is the intermediary that makes everything work. Understanding its role helps you debug problems and build more robust integrations.

Key concepts:

MCP Client, intermediary, connection management, protocol translation, session, state.

What it is:

The Server is the component that exposes tools, data, and prompts to the AI model. It implements the MCP protocol and responds to Client requests. This is what you’ll build in this course.

Why learn:

The Server is the main focus of this course. Everything you learn here prepares you to create your own MCP Servers that extend the capabilities of any AI model.

Key concepts:

MCP Server, tool exposure, resources, prompts, protocol implementation, endpoints.

What it is:

The complete MCP flow follows this path: User → Host → Client → Server → Tool → Server → Client → Host → User. Each step has a specific role, and the protocol ensures communication is standardized throughout.

Why learn:

Viewing the complete end-to-end flow is essential for debugging, optimizing, and creating integrations that work correctly in production.

Key concepts:

Request flow, request-response cycle, communication pipeline, component chaining.

What it is:

A mental diagram of the MCP architecture shows how Host, Client, and Server relate visually. The Host contains one or more Clients, each Client connects to exactly one Server, and each Server can expose multiple tools, resources, and prompts.

Why learn:

Having a clear mental model of the architecture lets you reason about complex problems and design elegant solutions.

Key concepts:

Architecture diagram, 1:N relationship, mental model, component composition, systems thinking.

What it is:

Practical examples of real-world MCP architectures: Claude Desktop (Host) using a filesystem server to access files, Cursor (Host) using a database server to query databases, and custom applications using multiple servers simultaneously.

Why learn:

Seeing concrete examples turns abstract concepts into practical knowledge. You'll recognize patterns you'll use in your own projects.

Key concepts:

Filesystem server, database server, GitHub server, multi-server setup, production scenarios.

Module 1.4 ~35 min · Hands-on

🎬 Seeing MCP in Action

Get hands-on for the first time: install, configure, and watch MCP work live with Claude Desktop.

What it is:

Claude Desktop is Anthropic's official application that serves as a Host for Claude. It supports MCP natively, letting you connect external tools to the model without writing integration code.

Why learn:

Claude Desktop will be your testing environment throughout the course. Installing and configuring it correctly is the first practical step toward using MCP.

Key concepts:

Claude Desktop, installation, supported platforms, minimum version, system requirements.

What it is:

The claude_desktop_config.json is where you declare which MCP Servers Claude Desktop should start. Each entry defines the command to run the server, its arguments, and environment variables.

Why learn:

This file is the entry point for any MCP integration in Claude Desktop. You’ll edit it frequently throughout the course to add new servers.

Key concepts:

claude_desktop_config.json, mcpServers, command, args, env, file location.

What it is:

The filesystem server is an official MCP Server that lets Claude access files and directories on your computer. Connecting it is as simple as adding a few lines to the configuration file.

Why learn:

This is your first real experience with a working MCP Server. Seeing Claude access your files is the “aha!” moment that solidifies your understanding of the protocol.

Key concepts:

@modelcontextprotocol/server-filesystem, npx, allowed directories, permissions, sandboxing.

What it is:

After configuring the filesystem server, you need to check that the connection is working. Claude Desktop shows visual indicators for connected servers, and you can test it by sending messages that require file access.

Why learn:

Knowing how to validate an MCP connection is an essential debugging skill. When something goes wrong with your own servers, you’ll know how to diagnose it.

Key concepts:

Connection check, visual indicators, error logs, troubleshooting, MCP handshake.

What it is:

With the filesystem server connected, you can ask Claude to list files, read content, create directories, and more. The model automatically identifies when it needs to use a tool and asks the user for permission.

Why learn:

Using tools in practice shows the real power of MCP. You’ll see how the model decides when and how to use tools, including the user permission mechanism.

Key concepts:

Tool calling, user approval, read_file, list_directory, write_file, tool use flow.

What it is:

Behind every interaction with the filesystem server, a complete JSON-RPC flow takes place: Claude identifies the need for a tool, the Client sends the request to the Server, the Server performs the action and returns the result, which is incorporated into the model's response.

Why learn:

Understanding what happens behind the interface is what separates a user from a developer. This knowledge is essential for creating your own MCP Servers.

Key concepts:

JSON-RPC, protocol messages, initialize, tools/list, tools/call, request-response cycle.

🧰 Types of Resources: Tools, Resources, Prompts

Discover the three types of resources an MCP Server can expose and when to use each one.

What it is:

Tools are functions the model can call to perform actions—such as reading a file, querying a database, or sending an email. They take parameters and return results, similar to function calls.

Why learn:

Tools are the most used MCP feature. Most servers you create will expose tools. Understanding their characteristics is essential for designing effective interfaces.

Key concepts:

Tool definition, input schema, output format, tool calling, side effects, idempotency.

What it is:

Resources are static or dynamic data that the model can access to enrich its context — such as documents, settings, logs, or data from an API. Unlike tools, resources are passive: they provide information without taking action.

Why learn:

Resources let you provide rich context to the model without needing tool calls. They’re ideal for data the model needs to consult frequently.

Key concepts:

Resource URI, MIME type, static vs. dynamic content, resource templates, on-demand reading.

What it is:

Prompts are instruction templates that the Server can offer to the Host. They let you create predefined workflows with parameterizable arguments that guide the model through complex tasks consistently.

Why learn:

Prompts are MCP's most underused feature, but they offer enormous power. They let you create guided experiences that turn the model into a specialized assistant.

Key concepts:

Prompt template, arguments, predefined messages, workflows, customization, consistency.

What it is:

Tools perform actions, Resources provide data, and Prompts guide behavior. Which one you choose depends on whether you want the model to do something (tool), know something (resource), or follow a pattern (prompt).

Why learn:

Choosing the right resource type for each situation is a fundamental design decision. Using the wrong type leads to confusing and inefficient experiences.

Key concepts:

Action vs. data vs. instruction, design decisions, model-controlled vs. user-controlled, side effects.

What it is:

Real examples of all three types: a tool that creates GitHub issues, a resource that exposes API documentation, and a prompt that guides the model through code review according to specific company standards.

Why learn:

Concrete examples solidify theoretical understanding and inspire ideas for your own servers. You’ll start seeing MCP opportunities in all your projects.

Key concepts:

GitHub tools, documentation as a resource, code review prompts, workflow automation, business scenarios.

What it is:

MCP's true power emerges when you combine tools, resources, and prompts in the same server. For example, a resource provides context, a prompt guides reasoning, and a tool performs the resulting action—all orchestrated by the model.

Why learn:

Combining all three types of resources is the key to creating sophisticated MCP Servers that offer rich, complete experiences for AI models.

Key concepts:

Resource composition, server design, integrated experience, model orchestration, design patterns.

Module 1.6 ~20 min · Theory

📡 Communication Transports

Understand how data travels between Client and Server through the different transport mechanisms available in MCP.

What it is:

Transports are the mechanisms that define how MCP messages travel between the Client and Server. They are the protocol’s communication layer, responsible for reliably sending and receiving JSON-RPC messages.

Why learn:

Choosing the right transport affects your solution's performance, security, and architecture. It's a fundamental design decision for any MCP Server.

Key concepts:

Transport layer, JSON-RPC, communication mechanism, reliability, latency.

What it is:

STDIO (Standard Input/Output) is the simplest MCP transport. The Client starts the Server as a child process and communicates through stdin and stdout. It's ideal for servers that run locally on the same machine as the Host.

Why learn:

STDIO is the transport you’ll use for most of the course. It’s simple, reliable, and doesn’t require network configuration. Most development servers use STDIO.

Key concepts:

stdin, stdout, child process, local communication, simplicity, no network.

What it is:

HTTP transport lets the MCP Server run as a remotely accessible web service. The Client sends HTTP POST requests with JSON-RPC messages and receives responses. It’s ideal for servers that need to be accessed by multiple clients or run on remote servers.

Why learn:

HTTP is the transport used in production environments and for shared servers. Understanding it prepares you to deploy MCP Servers that serve multiple users.

Key concepts:

HTTP POST, endpoints, web server, authentication, CORS, remote deployment.

What it is:

Server-Sent Events (SSE) is a transport that enables one-way streaming from the Server to the Client. Combined with HTTP POST to send messages to the Server, it creates a bidirectional communication channel ideal for long-running operations and real-time notifications.

Why learn:

SSE is important for scenarios that require real-time feedback, such as monitoring long-running processes or streaming partial results.

Key concepts:

Server-Sent Events, streaming, EventSource, persistent connection, push notifications, real time.

What it is:

Each transport has trade-offs: STDIO is the simplest, but only works locally. HTTP is versatile and works remotely, but doesn't support native streaming. SSE adds streaming, but requires more infrastructure. The choice depends on the use case.

Why learn:

Comparing transports gives you clear criteria for making architecture decisions. You’ll know how to justify your choice of transport in any project.

Key concepts:

Trade-offs, latency vs. simplicity, local vs. remote, scalability, infrastructure requirements.

What it is:

A practical guide to choosing a transport: use STDIO for development and personal servers, HTTP for production and shared servers, and SSE when you need streaming or real-time notifications. Also consider security, complexity, and maintenance.

Why learn:

Having a clear decision framework saves time and prevents future refactoring. You'll know how to choose the right transport from the start of each project.

Key concepts:

Decision framework, use cases, development vs. production, requirements checklist, migration between transports.
