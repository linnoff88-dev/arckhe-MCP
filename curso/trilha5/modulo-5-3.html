🔄 STDIO vs HTTP

O MCP suporta dois modelos de transporte: STDIO (entrada/saída padrêo) e HTTP (via rede). STDIO é local, simples e rápido — ideal para desenvolvimento e uso pessoal. HTTP é remoto, acessível pela rede e perfeito para deploy em cloud. A pergunta-chave é: quando migrar? Quando outros precisam acessar seu server — seja sua equipe, seus clientes ou sua infraestrutura de produçêo.

💎 Conceito Principal

STDIO funciona como um pipe Unix: o client lança o server como processo filho e se comunica via stdin/stdout. É zero-config e instantâneo, mas limitado à máquina local. HTTP expõe o server como um serviço web: qualquer client na rede pode se conectar via URL. Isso habilita cenários como múltiplos clients simultâneos, deploy em containers, e acesso de qualquer lugar do mundo. A troca é que HTTP exige configuraçêo de rede, segurança e infraestrutura — mas o ganho em flexibilidade é enorme.

❌ Evitar
  • •Usar HTTP para uso local quando STDIO basta
  • •Expor HTTP sem autenticaçêo na internet
  • •Manter STDIO quando múltiplos clients precisam acessar
  • •Ignorar a latência de rede ao migrar para HTTP
✅ Fazer
  • •Começar com STDIO para desenvolvimento rápido
  • •Migrar para HTTP quando precisar de acesso remoto
  • •Manter ambos os transportes disponíveis no código
  • •Testar localmente em HTTP antes de fazer deploy
📊 Dados e Pesquisa

A especificaçêo MCP define oficialmente dois transportes: STDIO e HTTP com SSE. Na prática, a maioria dos MCP Servers em produçêo utiliza HTTP/SSE para permitir integraçêo com múltiplos clients e deploy em nuvem. O protocolo HTTP adiciona tipicamente 1-5ms de latência por requisiçêo em redes locais, mas essa diferença é imperceptível comparada ao tempo de processamento das ferramentas. A versêo mais recente do protocolo também suporta Streamable HTTP, uma evoluçêo do SSE com melhor suporte a reconexêo.

2

🌐 Configurando HTTP no FastMCP

O FastMCP abstrai toda a complexidade de configurar um servidor HTTP. Com uma única linha de código, você troca o transporte de STDIO para HTTP ou SSE. O framework cuida de rotas, serializaçêo JSON-RPC, gerenciamento de conexões e streaming — você foca na lógica das suas tools.

💎 Conceito Principal

Configurar HTTP no FastMCP é trocar um único parâmetro:

# Antes — transporte STDIO (padrêo)
mcp.run()

# Depois — transporte HTTP
mcp.run(transport="http", host="0.0.0.0", port=8000)

# Ou com SSE (Server-Sent Events)
mcp.run(transport="sse", host="0.0.0.0", port=8000)

O parâmetro host="0.0.0.0" aceita conexões de qualquer IP (necessário para Docker/cloud). O port define a porta do servidor. O FastMCP usa internamente o uvicorn como servidor ASGI, garantindo performance e compatibilidade com o ecossistema Python.

💡 Dica Prática

Use uma variável de ambiente para alternar entre transportes sem modificar o código: transport = os.getenv("MCP_TRANSPORT", "stdio"). Em desenvolvimento local, use STDIO. Em produçêo, defina MCP_TRANSPORT=http. Assim, o mesmo código funciona em ambos os cenários sem nenhuma alteraçêo no source.

📋 Passos para migrar de STDIO para HTTP
Passo 1

Adicionar uvicorn e starlette às dependências no pyproject.toml.

Passo 2

Alterar mcp.run() para mcp.run(transport="http", host="0.0.0.0", port=8000).

Passo 3

Testar localmente acessando http://localhost:8000 e verificar que as tools respondem via HTTP.

📡 Server-Sent Events

SSE (Server-Sent Events) é uma tecnologia que permite o server enviar atualizações contínuas para o client via uma conexêo HTTP persistente. Diferente de WebSockets (bidirecional), SSE é unidirecional: o server envia, o client recebe. Isso é ideal para operações longas onde o client precisa acompanhar o progresso em tempo real.

💎 Conceito Principal

No transporte SSE do MCP, o client faz uma requisiçêo HTTP e mantém a conexêo aberta. O server envia mensagens JSON-RPC como eventos SSE conforme processa as requisições. Isso permite streaming de resultados parciais, notificações de progresso e respostas incrementais. O MCP usa SSE como canal de resposta enquanto o client envia requisições via POST normal. Essa arquitetura é robusta e funciona bem com proxies, load balancers e CDNs — diferente de WebSockets que requerem suporte especial de infraestrutura.

❌ Evitar
  • •Usar polling em vez de SSE para atualizações
  • •Nêo tratar reconexêo quando a conexêo SSE cai
  • •Enviar payloads enormes via SSE sem chunking
  • •Ignorar timeouts em operações longas
✅ Fazer
  • •Usar SSE para operações que demoram mais de 1s
  • •Implementar heartbeat para manter a conexêo viva
  • •Tratar reconexêo automática no client
  • •Enviar notificações de progresso para tools lentas
📊 Dados e Pesquisa

SSE é suportado nativamente por todos os browsers modernos e pela maioria dos frameworks HTTP. Comparado a WebSockets, SSE usa HTTP padrêo, o que significa compatibilidade total com proxies reversos (Nginx, Cloudflare) sem configuraçêo especial. A reconexêo automática é built-in na spec SSE — se a conexêo cair, o browser reconecta automaticamente usando o último Last-Event-ID. A evoluçêo do SSE no MCP é o Streamable HTTP, que combina POST para envio e SSE para recebimento em um único endpoint.

4

🔒 Segurança em HTTP

Expor um MCP Server via HTTP significa expô-lo à rede — e potencialmente à internet. Segurança nêo é opcional: HTTPS obrigatório em produçêo, autenticaçêo via headers, configuraçêo de CORS e rate limiting sêo o mínimo. Um server MCP sem proteçêo é uma porta aberta para execuçêo de código arbitrário.

💎 Conceito Principal

Checklist de segurança para MCP Server HTTP:

  • 1.HTTPS/TLS — criptografa o tráfego. Use Let's Encrypt ou o TLS do seu cloud provider.
  • 2.Autenticaçêo — valide tokens nos headers (Authorization: Bearer <token>).
  • 3.CORS — restrinja origens permitidas para evitar requisições de domínios nêo autorizados.
  • 4.Rate Limiting — limite requisições por IP/token para prevenir abuso.
  • 5.Firewall/VPN — em ambientes corporativos, restrinja acesso à rede interna.
🚨 Alerta

NUNCA use HTTP sem TLS em produçêo! Sem HTTPS, tokens de autenticaçêo, dados de requisições e respostas trafegam em texto puro — qualquer pessoa na mesma rede pode interceptar. Um MCP Server expõe tools que podem executar código, acessar bancos de dados e manipular arquivos. HTTP sem TLS em produçêo é equivalente a deixar a porta do cofre aberta com a senha colada na parede.

❌ Evitar
  • •HTTP puro em produçêo (sem TLS)
  • •Tokens hardcoded no código-fonte
  • •CORS com allow_origins=["*"] em produçêo
  • •Server exposto na internet sem autenticaçêo
✅ Fazer
  • •HTTPS com certificados válidos (Let's Encrypt)
  • •Tokens em variáveis de ambiente
  • •CORS restrito a domínios específicos
  • •Rate limiting + logging de acessos
5

☁️ Deploy em Nuvem

Com o server rodando via HTTP, o próximo passo é colocá-lo na nuvem. Existem diversas opções — desde plataformas simples como Railway e Fly.io até infraestrutura completa com AWS Lambda ou Docker em VPS. A escolha depende do seu orçamento, escala e necessidades de controle.

💎 Conceito Principal

Um Dockerfile básico para deploy do MCP Server:

FROM python:3.12-slim

WORKDIR /app
COPY . .

RUN pip install --no-cache-dir .

ENV MCP_TRANSPORT=http
ENV PORT=8000
EXPOSE 8000

CMD ["meu-server"]

O Dockerfile instala o pacote Python, define variáveis de ambiente e expõe a porta. Plataformas como Railway e Fly.io detectam automaticamente o Dockerfile e fazem o build. Para AWS Lambda, use um adapter como mangum para converter ASGI em Lambda handler.

📋 Passos para deploy
Passo 1

Criar o Dockerfile na raiz do projeto com a configuraçêo do server HTTP.

Passo 2

Configurar variáveis de ambiente na plataforma: tokens de API, MCP_TRANSPORT, porta e secrets.

Passo 3

Fazer push do código para o repositório Git conectado à plataforma — o deploy é automático.

Passo 4

Verificar os logs de deploy, testar a URL pública e configurar domínio customizado se necessário.

💡 Dica Prática

Para projetos pessoais e MVPs, Railway e Fly.io sêo as opções mais rápidas — deploy direto do GitHub em minutos, com HTTPS automático e tier gratuito. Para produçêo com mais controle, use Docker + VPS (Hetzner, DigitalOcean) com Nginx como reverse proxy e Let's Encrypt para TLS. Sempre use .dockerignore para excluir .env, .git e __pycache__.

6

🧪 Testando Remotamente

Com o server deployed, é hora de verificar que tudo funciona de fora — de outra máquina, de outra rede, como um client real faria. Testar remotamente revela problemas que testes locais escondem: firewalls, DNS, latência de rede e configurações de CORS.

💎 Conceito Principal

Testando com curl e configurando client remoto:

# Testar se o server responde
$ curl https://meu-server.railway.app/sse

# Configurar no Claude Desktop (claude_desktop_config.json)
{
  "mcpServers": {
    "meu-server": {
      "url": "https://meu-server.railway.app/sse"
    }
  }
}

Para clients HTTP/SSE, basta apontar a URL do server deployed. O client se conecta via HTTPS, mantém a conexêo SSE aberta e envia requisições normalmente. Verifique latência com curl -w "%{time_total}" para garantir que o tempo de resposta é aceitável.

💡 Dica Prática

Teste a partir de múltiplos ambientes: sua máquina local, uma VM em outra regiêo, e o celular (via hotspot 4G). Cada ambiente revela problemas diferentes — DNS pode falhar em uma rede, CORS pode bloquear em um browser, e latência pode ser inaceitável de outra regiêo. Use mcp-cli ou npx @modelcontextprotocol/inspector para inspecionar as mensagens JSON-RPC trocadas.

📋 Checklist de teste remoto
Passo 1

Verificar que a URL pública responde com curl — HTTP 200 no health check.

Passo 2

Conectar um MCP client remoto e listar as tools disponíveis com tools/list.

Passo 3

Executar uma tool e medir a latência — verificar que o tempo de resposta é menor que 5 segundos para operações simples.

📝 Resumo do Módulo

  • ✓ STDIO é local e simples; HTTP é remoto e escalável — migre quando outros precisam acessar seu server.
  • ✓ FastMCP abstrai a complexidade — trocar de STDIO para HTTP é alterar um parâmetro em mcp.run().
  • ✓ SSE permite streaming e atualizações contínuas via conexêo HTTP persistente.
  • ✓ Segurança é obrigatória: HTTPS, autenticaçêo, CORS e rate limiting sêo o mínimo.
  • ✓ Deploy em nuvem com Docker — Railway, Fly.io ou VPS com Nginx e Let's Encrypt.
  • ✓ Teste remotamente de múltiplos ambientes para garantir que o server funciona para todos.
