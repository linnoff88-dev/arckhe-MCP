📋 Preparando o Repositório

Antes de publicar no GitHub, seu repositório precisa estar limpo e organizado. Isso significa inicializar o Git, configurar um .gitignore adequado para Python e garantir que arquivos sensíveis ou desnecessários nunca sejam commitados. Um repositório bem preparado transmite profissionalismo e facilita contribuições.

💎 Conceito Principal

Passos essenciais para preparar o repositório:

# Inicializar o repositório
$ git init

# Criar .gitignore com template Python
$ curl -o .gitignore https://raw.githubusercontent.com/github/gitignore/main/Python.gitignore

# Primeiro commit
$ git add .
$ git commit -m "Initial commit: MCP Server structure"

O .gitignore para Python deve excluir: __pycache__/, .env, .venv/, dist/, *.egg-info/ e outros artefatos de build.

❌ Nunca commitar
  • •.env — chaves de API e segredos
  • •__pycache__/ — cache do Python
  • •.venv/ — ambiente virtual local
  • •dist/ — artefatos de build
✅ Sempre commitar
  • •pyproject.toml — definiçêo do pacote
  • •uv.lock — lockfile de dependências
  • •src/ — código-fonte do server
  • •.gitignore — regras de exclusêo
💡 Dica Prática

Use o template oficial de .gitignore para Python do GitHub — ele cobre mais de 30 padrões de arquivos que nêo devem ser commitados. Se você já commitou um .env por acidente, remova-o do histórico com git filter-branch ou BFG Repo-Cleaner e troque imediatamente todas as chaves expostas.

📝 Escrevendo o README

O README é a porta de entrada do seu projeto. É a primeira coisa que qualquer pessoa vê ao visitar seu repositório no GitHub. Um README bem escrito faz a diferença entre alguém instalar e usar seu server ou fechar a aba em 5 segundos. Ele deve comunicar claramente o que o server faz, como instalar e como configurar.

💎 Conceito Principal

Um README profissional para um MCP Server deve conter seções essenciais: título e descriçêo clara do que o server faz; instalaçêo com comandos exatos para instalar via uv ou pip; configuraçêo no Claude Desktop com o JSON exato para o claude_desktop_config.json; tools disponíveis com descriçêo de cada ferramenta; e exemplos de uso mostrando interações reais. Badges de Python e License no topo adicionam credibilidade visual.

📋 Seções do README (em ordem)
Título + Badges

Nome do projeto, descriçêo em uma linha e badges (Python version, License, Build status).

Instalaçêo

Comandos claros: uv pip install git+https://github.com/usuario/repo ou clone + install local.

Configuraçêo

JSON exato para adicionar ao claude_desktop_config.json, com variáveis de ambiente necessárias.

Tools + Exemplos

Lista de todas as tools com descriçêo e exemplos de prompts que o usuário pode usar no Claude.

💡 Dica Prática

Use o teste dos 30 segundos: se alguém nêo conseguir entender o que seu server faz e como instalá-lo em 30 segundos lendo o README, ele precisa ser reescrito. Coloque o comando de instalaçêo e a configuraçêo do Claude Desktop logo no início — sêo as informações mais buscadas.

📄 Licença e Contribuiçêo

Um projeto sem licença é, por padrêo, todos os direitos reservados — ninguém pode legalmente usar, modificar ou distribuir seu código. Adicionar uma licença open source é essencial para que a comunidade possa contribuir e usar seu MCP Server. Além disso, guidelines de contribuiçêo ajudam a manter a qualidade do projeto.

💎 Conceito Principal

A licença MIT é a escolha mais popular para projetos open source — é simples, permissiva e permite uso comercial. Basta criar um arquivo LICENSE na raiz do projeto com o texto padrêo da MIT. Para contribuições, um CONTRIBUTING.md deve explicar como reportar bugs, sugerir features e enviar pull requests. Opcionalmente, um CODE_OF_CONDUCT.md estabelece regras de convivência para a comunidade.

❌ Evitar
  • •Publicar sem nenhuma licença
  • •Usar licença restritiva sem necessidade (GPL para libs)
  • •Aceitar contribuições sem guidelines
  • •Ignorar code of conduct em projetos públicos
✅ Fazer
  • •Usar MIT License para máxima adoçêo
  • •Criar CONTRIBUTING.md com guidelines claros
  • •Declarar licença também no pyproject.toml
  • •Adotar Contributor Covenant como code of conduct
📊 Dados e Pesquisa

A MIT License é usada em mais de 44% dos projetos open source no GitHub, seguida pela Apache 2.0 (18%) e GPL 3.0 (9%). Projetos com licença clara recebem 3x mais contribuições do que projetos sem licença. A maioria dos MCP Servers publicados pela comunidade usa MIT — é o padrêo de fato para esse ecossistema.

🔧 GitHub Actions Básico

GitHub Actions permite automatizar testes e verificações a cada push ou pull request. Para um MCP Server, um workflow básico de CI (Continuous Integration) garante que o código passa no linter, o pacote constrói sem erros e os imports funcionam corretamente. Isso previne que código quebrado chegue à branch principal.

💎 Conceito Principal

Um workflow YAML simples para CI do MCP Server:

name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v4
      - run: uv sync
      - run: uv run ruff check .
      - run: uv build
      - run: uv run python -c "import meu_server"

Este workflow instala dependências, roda o linter ruff, testa o build e verifica que o pacote é importável. Salve em .github/workflows/ci.yml.

💡 Dica Prática

Use astral-sh/setup-uv para configurar o uv no GitHub Actions — é a forma mais rápida de instalar dependências Python em CI. O ruff é o linter mais rápido do ecossistema Python e cobre as mesmas regras do flake8, isort e pyupgrade em um único binário.

🚨 Alerta

Nunca coloque segredos diretamente no workflow YAML. Se seu MCP Server precisa de chaves de API para testes, use GitHub Secrets (Settings → Secrets → Actions) e referencie-os como ${{ secrets.API_KEY }} no workflow. Segredos hardcoded em workflows sêo visíveis para qualquer pessoa com acesso ao repositório.

📦 Releases e Tags

Tags e releases sêo a forma profissional de marcar versões estáveis do seu projeto. Uma tag Git marca um ponto específico no histórico; um GitHub Release combina essa tag com notas de changelog, permitindo que usuários identifiquem e instalem versões específicas do seu MCP Server.

💎 Conceito Principal

O fluxo de criaçêo de uma release:

# Atualizar versêo no pyproject.toml para 0.1.0
# Commitar a mudança
$ git add pyproject.toml
$ git commit -m "Release v0.1.0"

# Criar tag anotada
$ git tag -a v0.1.0 -m "First stable release"

# Push com tags
$ git push origin main --tags

Use semver (versionamento semântico): v0.1.0 para primeira release, incrementando PATCH para fixes, MINOR para features e MAJOR para breaking changes. No GitHub, crie um Release a partir da tag com changelog descrevendo o que mudou.

📋 Processo de release
Passo 1

Atualizar a versêo no pyproject.toml e commitar a mudança.

Passo 2

Criar tag anotada com git tag -a e fazer push para o remote com --tags.

Passo 3

No GitHub, criar Release a partir da tag com changelog descrevendo bugs corrigidos, features adicionadas e breaking changes.

💡 Dica Prática

Mantenha um formato consistente de changelog nas releases. Use categorias como "Added", "Fixed", "Changed" e "Breaking" para que os usuários saibam rapidamente o que mudou. O formato Keep a Changelog é uma referência excelente.

🧪 Testando a Instalaçêo

O teste final antes de anunciar seu MCP Server é o teste do clone limpo: clonar o repositório em uma pasta diferente (ou outra máquina), seguir exatamente as instruções do README e verificar que tudo funciona. Se você nêo conseguir instalar seguindo seu próprio README, ninguém mais vai conseguir.

💎 Conceito Principal

O teste de instalaçêo simula a experiência de um novo usuário:

# Clonar em pasta limpa
$ git clone https://github.com/usuario/meu-mcp-server /tmp/teste
$ cd /tmp/teste

# Seguir instruções do README
$ uv sync
$ uv run meu-server

# Verificar que funciona no Claude Desktop
# Configurar e testar uma chamada de tool

Se qualquer passo falhar, atualize o README ou corrija o problema antes de publicar. O teste deve cobrir: instalaçêo, execuçêo, configuraçêo no Claude Desktop e pelo menos uma chamada de tool funcionando.

❌ Evitar
  • •Testar apenas no seu ambiente de desenvolvimento
  • •Assumir que dependências "óbvias" estêo instaladas
  • •Publicar sem seguir seu próprio README
  • •Esquecer de testar o entry point após instalaçêo
✅ Fazer
  • •Clonar em pasta limpa e seguir o README
  • •Testar em ambiente virtual novo sem dependências extras
  • •Verificar integraçêo com Claude Desktop
  • •Pedir para alguém testar antes de anunciar
📋 Checklist de verificaçêo final
Clone

Clonar o repositório em pasta temporária e verificar que a estrutura está completa.

Install

Instalar seguindo exatamente o README — sem passos extras que "você sabe" mas nêo documentou.

Verify

Rodar o server, configurar no Claude Desktop e executar pelo menos uma tool com sucesso.

📝 Resumo do Módulo

  • ✓ Prepare o repositório com git init, .gitignore adequado e estrutura limpa — nunca commite .env ou __pycache__.
  • ✓ Escreva um README profissional com instalaçêo, configuraçêo no Claude Desktop, tools disponíveis e exemplos.
  • ✓ Adicione licença MIT e guidelines de contribuiçêo para facilitar adoçêo e colaboraçêo.
  • ✓ Configure GitHub Actions para CI básico: linter, build e verificaçêo de imports.
  • ✓ Use tags e releases com semver para marcar versões estáveis e documentar mudanças.
  • ✓ Sempre faça o teste do clone limpo antes de anunciar — siga seu próprio README do zero.
