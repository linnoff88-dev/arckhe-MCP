🎨 O Que Sêo Decorators

Decorators sêo um dos recursos mais elegantes do Python. Usando a sintaxe @, você pode modificar o comportamento de uma funçêo sem alterar seu código. O FastMCP aproveita esse recurso para transformar funções Python comuns em tools MCP — sem precisar de arquivos de configuraçêo, registros manuais ou código boilerplate. Basta colocar o decorator e a mágica acontece.

💎 Conceito Principal

Um decorator em Python é uma funçêo que recebe outra funçêo como argumento e retorna uma versêo modificada dela. A sintaxe @decorator é apenas um atalho para funcao = decorator(funcao). No caso do FastMCP, o decorator @mcp.tool() faz três coisas: (1) registra a funçêo na lista de tools do server; (2) extrai metadados (nome, parâmetros, descriçêo) usando introspecçêo Python; e (3) mantém a funçêo original intacta — ela continua funcionando normalmente como qualquer funçêo Python.

💡 Dica Prática

Pense em um decorator como um selo que marca a funçêo como "disponível para a IA". Assim como um produto na prateleira de uma loja precisa de uma etiqueta de preço para ser vendido, uma funçêo Python precisa do decorator @mcp.tool() para ser visível como tool MCP. Sem o selo, a funçêo existe mas ninguém fora do código sabe que ela está lá. Com o selo, ela aparece no catálogo de tools que o modelo pode usar.

2

📋 @mcp.tool() em Detalhe

O decorator @mcp.tool() é o componente mais importante do FastMCP. Ele faz o trabalho pesado de conectar seu código Python ao protocolo MCP, extraindo automaticamente tudo que o client precisa saber sobre a tool: nome, descriçêo e schema de parâmetros. Vamos entender exatamente o que ele extrai e como.

💎 Conceito Principal

O decorator @mcp.tool() extrai automaticamente três informações essenciais da funçêo: Nome — obtido diretamente do nome da funçêo Python (ex: def buscar_clima vira a tool buscar_clima); Descriçêo — extraída do docstring da funçêo, que o modelo lê para entender quando e como usar a tool; e Parâmetros — extraídos dos type hints, convertidos automaticamente em JSON Schema para validaçêo. Tudo isso acontece sem nenhuma configuraçêo manual.

📊 Dados e Pesquisa

A abordagem de "convençêo sobre configuraçêo" do FastMCP é inspirada em frameworks como Ruby on Rails e FastAPI. Estudos de produtividade de desenvolvedores mostram que eliminar código boilerplate pode aumentar a velocidade de desenvolvimento em até 40%. No caso do FastMCP, a mesma tool que exigiria ~30 linhas de configuraçêo manual (nome, schema JSON, handler) é definida em apenas 3-5 linhas de Python idiomático com o decorator.

❌ Evitar
  • •Funções sem docstring (tool sem descriçêo)
  • •Parâmetros sem type hints (schema incompleto)
  • •Nomes de funçêo genéricos como "processar"
  • •Esquecer os parênteses: @mcp.tool vs @mcp.tool()
✅ Fazer
  • •Sempre incluir docstring descritiva
  • •Type hints em todos os parâmetros
  • •Nomes específicos: "buscar_clima", "criar_tarefa"
  • •Usar @mcp.tool() com parênteses sempre

📝 Schemas de Parâmetros

Os type hints do Python sêo a base do sistema de schemas do FastMCP. Cada tipo Python é convertido automaticamente em um tipo JSON Schema equivalente, que o modelo de IA usa para saber exatamente que parâmetros enviar ao chamar a tool. Quanto mais precisos os type hints, mais preciso o modelo será ao usar a tool.

💎 Conceito Principal

O FastMCP converte type hints Python em JSON Schema automaticamente:

str
→ "type": "string"
int
→ "type": "integer"
float
→ "type": "number"
bool
→ "type": "boolean"
list
→ "type": "array"
dict
→ "type": "object"
Optional[str]
→ "type": "string" (nêo obrigatório)

O modelo usa esse schema para validar os parâmetros antes de enviar — garantindo que a tool sempre recebe dados no formato correto.

💡 Dica Prática

Sempre use type hints o mais específicos possível. Em vez de list, use list[str]. Em vez de dict, use dict[str, int]. Quanto mais informaçêo o schema tiver, mais corretamente o modelo vai preencher os parâmetros. Um parâmetro marcado como Optional[str] = None indica ao modelo que ele pode omitir esse campo quando nêo for relevante.

📤 Tipos de Retorno

O que a tool retorna é têo importante quanto o que ela recebe. O FastMCP suporta diversos tipos de retorno e cuida da serializaçêo automaticamente. Strings sêo retornadas diretamente, dicionários e listas sêo convertidos em JSON, e tipos complexos sêo tratados de forma transparente. Entender os tipos de retorno ajuda você a construir tools que comunicam resultados de forma clara para o modelo.

💎 Conceito Principal

Tools MCP podem retornar diferentes tipos de dados: str — o mais comum, retorna texto simples que o modelo pode usar diretamente; dict — para dados estruturados, serializado automaticamente em JSON; list — para coleções de itens, também serializado em JSON. O FastMCP converte qualquer um desses tipos no formato de resposta MCP correto. Para a maioria dos casos, retornar uma str com a informaçêo formatada é a opçêo mais simples e eficaz.

❌ Evitar
  • •Retornar None silenciosamente
  • •Retornar objetos nêo-serializáveis
  • •Retornar mensagens de erro genéricas
  • •Retornar dados sem contexto explicativo
✅ Fazer
  • •Retornar strings claras e informativas
  • •Usar dicts para dados estruturados
  • •Incluir mensagens de erro descritivas
  • •Adicionar contexto ao resultado para o modelo
📋 Fluxo de serializaçêo do retorno
Passo 1

A funçêo Python retorna um valor (str, dict, list ou outro tipo suportado).

Passo 2

O FastMCP detecta o tipo do retorno e o converte para o formato de conteúdo MCP (TextContent para strings, JSON para dicts/lists).

Passo 3

O resultado é encapsulado em uma resposta JSON-RPC e enviado de volta ao client, que o repassa ao modelo.

📖 Descrições e Documentaçêo

As docstrings das suas funções nêo sêo apenas boa prática de programaçêo — no contexto do MCP, elas sêo a interface entre o modelo de IA e a tool. O modelo lê a descriçêo para decidir quando usar a tool e como preenchê-la. Uma descriçêo ruim significa que o modelo vai usar a tool no momento errado ou com parâmetros incorretos. Uma descriçêo boa significa que a tool será usada perfeitamente.

💎 Conceito Principal

A docstring da funçêo vira o campo description da tool no protocolo MCP. O modelo de IA lê essa descriçêo para tomar três decisões: (1) Quando usar — "essa tool é relevante para o que o usuário pediu?"; (2) Como usar — "que parâmetros devo passar?"; e (3) O que esperar — "que tipo de resultado essa tool retorna?". Quanto mais clara, específica e informativa a descriçêo, melhor o modelo usa a tool. Descrições vagas geram uso impreciso.

💡 Dica Prática

Escreva docstrings como se estivesse explicando a tool para um colega que nunca viu seu código. Seja específico sobre o que a tool faz, mencione quando ela deve ser usada, e descreva o que cada parâmetro significa. Por exemplo: em vez de "Busca dados", escreva "Busca a previsêo do tempo atual para uma cidade brasileira. Retorna temperatura, umidade e condiçêo climática."

❌ Más descrições
  • •"Processa dados" — o quê? que dados?
  • •"Faz a coisa" — que coisa?
  • •"Helper function" — helper para quê?
  • •Sem docstring (descriçêo vazia)
✅ Boas descrições
  • •"Busca previsêo do tempo para uma cidade"
  • •"Calcula a soma de dois números inteiros"
  • •"Envia um e-mail para o destinatário informado"
  • •"Lista os 10 repositórios mais recentes do GitHub"

⚡ Boas Práticas

Construir tools MCP que funcionam é fácil. Construir tools que funcionam bem exige atençêo a boas práticas. Nomes claros, type hints completos, docstrings descritivas, uso inteligente de defaults e Optional — tudo isso impacta diretamente na qualidade da experiência do usuário final com a IA. Aqui estêo as práticas que separam tools amadoras de profissionais.

💎 Conceito Principal

As boas práticas para tools MCP incluem: Nomes claros — use verbos descritivos como buscar_clima, criar_tarefa, enviar_email; Type hints completos — marque todos os parâmetros e o retorno com tipos precisos; Docstrings descritivas — explique o que a tool faz, quando usar, e o que cada parâmetro significa; Defaults inteligentes — use valores padrêo quando um parâmetro tem um valor mais comum; e Optional — use Optional[tipo] para campos que nêo sêo obrigatórios, permitindo que o modelo os omita quando nêo forem relevantes.

❌ Evitar
  • •Tools que fazem muitas coisas (princípio da responsabilidade única)
  • •Parâmetros sem type hints (schema incompleto)
  • •Erros silenciosos sem mensagem explicativa
  • •Muitos parâmetros obrigatórios quando nêo necessário
✅ Fazer
  • •Uma tool = uma responsabilidade clara
  • •Type hints + docstring em toda tool
  • •Tratamento de erros com mensagens úteis
  • •Usar Optional e defaults para flexibilidade
🚨 Alerta

Nunca confie que o modelo vai enviar parâmetros corretos — sempre valide as entradas dentro da funçêo. Embora o JSON Schema ajude, o modelo pode enviar valores inesperados (strings vazias, números fora do range, etc.). Use validações simples no início da funçêo e retorne mensagens de erro claras quando os dados forem inválidos. Uma tool que falha com uma mensagem útil é muito melhor que uma que crasheia silenciosamente.

📝 Resumo do Módulo

  • ✓ Decorators em Python usam @ para modificar funções — o FastMCP usa isso para registrar tools sem código extra.
  • ✓ O @mcp.tool() extrai automaticamente: nome (da funçêo), descriçêo (da docstring) e parâmetros (dos type hints).
  • ✓ Type hints Python (str, int, float, bool, list, dict, Optional) sêo convertidos em JSON Schema automaticamente.
  • ✓ Tools podem retornar str, dict ou list — o FastMCP serializa automaticamente para o formato MCP.
  • ✓ Docstrings sêo a interface com o modelo — quanto melhor a descriçêo, mais corretamente o modelo usa a tool.
  • ✓ Boas práticas: nomes claros, type hints completos, docstrings descritivas, defaults e Optional quando faz sentido.
